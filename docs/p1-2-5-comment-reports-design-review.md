# P1-2.5 댓글 신고·운영 제재 설계 리뷰

## 리뷰 결론

초기 설계 방향은 타당하다. 다만 신고 수를 곧바로 댓글 공개 상태에 연결하면 집단 신고로 검열이 가능한 구조가 되므로 자동 임계치 제재는 도입하지 않는다. 모든 숨김·차단은 관리자 결정으로만 수행한다.

## 발견 사항과 보완

### 1. 신고 수 기반 자동 숨김 위험

**문제**

신고 수가 일정 기준을 넘으면 자동 숨김하는 방식은 다계정 또는 조직적 신고에 취약하다.

**보완**

- 신고는 관리자 대기열 우선순위 입력으로만 사용한다.
- 신고 수만으로 댓글 상태를 변경하지 않는다.
- 자동 Moderation 결과와 신고 집계는 별도 증거로 유지한다.

### 2. 신고자 탈퇴와 감사 기록 보존

**문제**

`reporter_id`를 `ON DELETE CASCADE`로 두면 신고자가 탈퇴할 때 운영 판단의 근거가 사라진다.

**보완**

- `reporter_id`는 nullable이며 `ON DELETE SET NULL`을 사용한다.
- 신고 내용과 처리 기록은 남긴다.
- 관리자 RPC에서도 신고자 식별 정보는 반환하지 않는다.

### 3. 중복 신고 정책의 모호성

**문제**

처리 완료 후 동일 사용자가 다시 신고할 수 있으면 운영자를 반복적으로 괴롭힐 수 있다.

**보완**

- `(comment_id, reporter_id)` 유일성은 상태와 무관하게 영구 적용한다.
- 신고 결과가 처리된 뒤에도 UI는 `신고됨`으로 표시한다.
- 댓글이 수정된 뒤 재신고하는 기능은 이번 범위에서 제외한다.

### 4. 사건 처리 중 신규 신고 경쟁 조건

**문제**

관리자가 3건으로 본 사건에 처리 직전 네 번째 신고가 추가되면 일부 신고가 미처리 상태로 남거나 잘못 묶일 수 있다.

**보완**

- 신고 생성과 사건 처리 모두 댓글 ID 기반 advisory lock을 획득한다.
- 관리자 RPC는 `expected_pending_count`를 검증한다.
- 불일치 시 `40001`로 실패시키고 대기열 재조회를 요구한다.

### 5. 댓글 Moderation과 신고 처리 원자성

**문제**

신고를 resolved로 바꾼 뒤 댓글 숨김에 실패하면 사건은 처리됐지만 댓글은 공개된 상태가 될 수 있다.

**보완**

- 사건 decision 삽입, 기존 Moderation review 호출, 신고 상태 변경을 하나의 RPC 트랜잭션에서 수행한다.
- 숨김·차단은 검증된 `private.apply_moderation_review`를 재사용한다.
- 어느 단계든 실패하면 전체 롤백한다.

### 6. 삭제된 댓글의 사건 처리

**문제**

신고 후 작성자가 댓글을 삭제할 수 있다. 사건을 대기열에서 제거하면 신고 증거가 사라지고, 그대로 두면 숨김·차단 조치가 의미가 없다.

**보완**

- 삭제된 댓글 사건도 관리자 대기열과 감사 기록에는 유지한다.
- 삭제 댓글에는 `dismissed` 또는 `kept`만 허용한다.
- `hidden`과 `blocked`는 명시적으로 거부한다.
- 공개 댓글 목록에는 기존 Tombstone 규칙을 유지한다.

### 7. 신고 상세 설명의 개인정보 위험

**문제**

신고자가 상세 사유에 이메일, 전화번호 등 개인정보를 입력할 수 있다.

**보완**

- 상세 사유는 일반 사용자와 댓글 작성자에게 절대 반환하지 않는다.
- 관리자 대기열에는 신고자 정보 없이 최대 10개의 최근 상세 사유만 반환한다.
- 입력은 일반 텍스트, 500자 제한, 공백 정규화만 수행한다.
- 후속 retention 단계에서 오래된 상세 사유 redaction을 검토한다.

### 8. 작성자 경고의 의미

**문제**

`warning`을 계정 정지처럼 처리하면 별도 정책, 이의제기, 만료, 알림 시스템 없이 권한 제재가 발생한다.

**보완**

- 이번 단계의 warning은 append-only 운영 이벤트다.
- 인증 권한과 계정 상태는 변경하지 않는다.
- 경고 선택 시 10자 이상의 관리자 메모를 요구한다.
- 후속 계정 제재 시스템이 누적 경고를 입력으로 사용한다.

### 9. 사유 체계 분리

**문제**

사용자 신고 사유와 기존 Moderation 사유는 의미와 세분화 수준이 다르다.

**보완**

- `comment_reports.reason`은 사용자 친화적 신고 사유 집합을 사용한다.
- 숨김·차단 시 관리자가 기존 Moderation 사유를 별도로 선택한다.
- `kept`와 `dismissed`는 Moderation 사유를 `none`으로 기록한다.

### 10. 신고 완료 상태 조회의 정보 노출

**문제**

댓글별 전체 신고 수나 타인의 신고 여부를 공개하면 여론 몰이와 추가 신고를 유도할 수 있다.

**보완**

- 공개 UI는 오직 `reported_by_me` boolean만 표시한다.
- 전체 신고 수는 관리자에게만 제공한다.
- authenticated 전용 ID 배열 RPC로 현재 사용자의 신고 여부만 조회한다.

### 11. 관리자 대기열 응답 크기

**문제**

댓글 하나에 신고가 많이 쌓이면 모든 상세 설명을 JSON으로 반환하는 쿼리가 비대해진다.

**보완**

- 대기열은 댓글 단위로 페이지네이션한다.
- 사유는 집계 JSON으로 반환한다.
- 상세 설명은 최근 10개 비식별 샘플만 반환한다.
- 신고자 ID 및 프로필 join은 하지 않는다.

### 12. 관리자 대시보드 집계 의미

**문제**

신고 행 수를 표시하면 한 댓글에 신고가 몰린 경우 실제 검토 작업량보다 과장된다.

**보완**

- 대시보드는 pending 신고 행 수가 아니라 distinct 댓글 사건 수를 표시한다.

## 최종 설계 승인 조건

다음 조건을 구현에 강제한다.

1. 테이블 직접 접근 권한 없음
2. 동일 사용자·댓글 영구 중복 신고 방지
3. 시간당 5건, 24시간 15건 제한
4. 신고 수 자동 제재 없음
5. 신고자 정보 비노출
6. 사건 advisory lock 및 stale count 검증
7. Moderation 변경과 신고 처리의 단일 트랜잭션
8. 삭제 댓글 제재 금지
9. warning은 감사 이벤트로만 저장
10. PR exact-head CI 성공 전 완료 판정 금지
