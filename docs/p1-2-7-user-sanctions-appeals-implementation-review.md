# P1-2.7 사용자 제재·이의제기 구현 리뷰

## 검토 범위

- Append-only 제재 원장과 이벤트 원장
- 현재 상태 projection
- 관리자 제재·해제 RPC
- 사용자 단일 이의제기 및 관리자 수용·기각
- 댓글·신고·좋아요·북마크 capability enforcement
- 사용자·관리자 화면
- 제재 관련 알림

## 확인된 보완

1. 기간 만료 후에도 이의제기가 수용될 수 있으므로 `expired` 이벤트와 `overturned` 이벤트가 함께 존재할 수 있게 고유 제약을 분리했다.
2. 경고는 기간이 없는 감사 기록으로 취급하고 capability 차단에는 사용하지 않는다.
3. 같은 종류의 유효한 기간제 제재가 중복 생성되지 않게 대상 사용자 단위 advisory lock과 활성 상태 검사를 적용했다.
4. 계정 정지는 댓글·신고뿐 아니라 좋아요·북마크 같은 비필수 쓰기도 차단한다.
5. 제재 조회와 이의제기 제출은 계정 정지 중에도 허용한다.
6. 신고 사건의 기존 `warning` 결정을 제재 원장으로 이관하되 기존 알림과 중복되지 않게 신규 제재 알림은 생성하지 않는다.
7. 관리자 계정은 이 제재 시스템의 대상에서 제외했다.
8. 원장·이의제기·결정은 UPDATE/DELETE를 차단하고 현재 상태 projection만 내부 함수가 갱신한다.

## 잔여 운영 사항

- `expire_due_user_sanctions`는 service role 스케줄러에서 주기적으로 호출해야 한다.
- UI 검색은 초기 단계에서 사용자 UUID 직접 입력을 지원하며, DB에는 표시명/UUID 검색 RPC도 준비했다.
- 영구 정지는 현재 범위에서 제외했다.
