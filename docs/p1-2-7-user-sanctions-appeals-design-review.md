# P1-2.7 사용자 계정 제재·이의제기 설계 리뷰

## 리뷰 결론

계정 제재를 단일 mutable 상태 컬럼으로 구현하지 않고 최초 결정, 상태 전환 원장, 현재 projection을 분리하는 방향은 타당하다. 다만 관리자 계정 보호, 만료 전후 이의제기, 기존 경고 알림과의 중복, projection 지연 시 정책 판정 등 몇 가지 경계 조건을 명시적으로 보완해야 한다.

## 발견 사항과 보완

### 1. 관리자 계정 상호 제재 위험

**문제**

일반 admin 권한만 확인하면 한 관리자가 다른 관리자를 활동 정지시켜 운영 통제권을 탈취할 수 있다.

**보완**

- 모든 제재 부여 RPC는 대상 사용자의 `user_roles.admin` 여부를 검사한다.
- 관리자 계정은 이번 단계의 제재 대상에서 제외한다.
- 관리자 제재가 필요하면 후속 최고 관리자 또는 별도 보안 절차로 처리한다.

### 2. 경고 중복 정책

**문제**

동일 종류 active 제재 중복 금지를 `warning`에도 적용하면 반복 위반의 개별 경고 근거를 기록할 수 없다.

**보완**

- `warning`은 중복 허용한다.
- 댓글·신고 제한과 계정 정지만 동일 종류의 현재 유효 제재를 중복 부여하지 않는다.
- 경고 수는 자동 제재 조건으로 사용하지 않는다.

### 3. projection 만료 지연

**문제**

주기 작업이 지연되면 상태가 `active`로 남아 만료된 사용자를 계속 차단할 수 있다.

**보완**

- 기능 강제는 projection 상태뿐 아니라 `starts_at <= now()` 및 `ends_at > now()`를 함께 확인한다.
- 만료 작업은 감사 상태를 정리하는 용도이며 권한 판정의 정확성 전제조건이 아니다.
- 사용자·관리자 목록의 표시 상태도 시간 범위를 고려한 effective state를 반환한다.

### 4. 만료 후 이의제기

**문제**

단기 제재가 관리자 검토 전에 만료되면 이의제기 권리가 사라질 수 있다.

**보완**

- `warning`은 overturned 전까지 언제든 한 번 이의제기할 수 있다.
- 기간 제재는 유효 중이거나 종료 후 30일 이내에 한 번 이의제기할 수 있다.
- 이미 `revoked` 또는 `overturned`된 제재에는 새 이의제기를 받지 않는다.
- 만료 후 수용된 이의제기는 `overturned` 이벤트로 역사적 결정을 취소한다.

### 5. 이의제기 수용과 수동 해제의 의미 혼합

**문제**

이의제기 수용을 `revoked`로 기록하면 원결정이 잘못됐다는 의미와 단순 조기 해제가 구분되지 않는다.

**보완**

- 운영자 조기 해제는 `revoked`다.
- 이의제기 수용은 `overturned`다.
- 자연 만료는 `expired`다.
- 세 종료 사유는 projection과 알림에서 구분한다.

### 6. 기존 댓글 신고 경고와 알림 중복

**문제**

댓글 신고 결정의 `author_action=warning`은 이미 `comment_author_warning` 알림을 생성한다. 동일 결정에서 `user_sanction_imposed`를 추가하면 사용자가 같은 사실을 두 번 받는다.

**보완**

- 신고 결정에서 자동 생성된 warning sanction은 별도 제재 부여 알림을 생성하지 않는다.
- 기존 `comment_author_warning` 알림을 사용자 고지로 재사용한다.
- 관리자 화면에서 직접 생성한 warning만 `user_sanction_imposed` 알림을 생성한다.

### 7. 알림 실패와 제재 트랜잭션

**문제**

알림이 보조 데이터라는 이유로 실패를 무시하면 사용자가 기능 차단 이유를 모를 수 있다. 반대로 알림 장애가 운영 결정을 막을 수 있다.

**보완**

이번 단계에서는 제재 부여·해제·이의제기 결과와 알림을 원자적으로 처리한다. 제재 알림 계약은 단순하고 내부 테이블에 국한되므로 사용자 고지 보장을 우선한다. 향후 외부 이메일·푸시가 추가되면 outbox로 분리한다.

### 8. Auth 사용자 삭제와 감사 기록

**문제**

대상 사용자 FK를 cascade로 두면 계정 삭제 시 제재 원장이 사라질 수 있다.

**보완**

- `target_user_id`는 `auth.users ON DELETE RESTRICT`로 보존한다.
- 관리자·이의제기 처리자 식별자는 `ON DELETE SET NULL`로 두어 원장을 유지한다.
- 계정 삭제와 법적 보존 정책은 별도 anonymization 단계에서 다룬다.

### 9. 원본 근거 삭제

**문제**

근거 댓글, 신고 결정, Moderation review가 삭제되면 제재 판단의 traceability가 손상된다.

**보완**

- 근거 FK는 `ON DELETE RESTRICT`를 사용한다.
- 원본 테이블의 기존 append-only 또는 soft-delete 정책을 유지한다.
- 사용자 반환 RPC는 내부 관리자 메모나 신고자 정보를 노출하지 않는다.

### 10. 계정 정지의 범위

**문제**

댓글만 차단하면 `account_suspension`이라는 이름과 실제 효력이 불일치한다.

**보완**

- 댓글 작성·수정, 신고, 좋아요, 북마크를 DB에서 차단한다.
- 읽기, 로그아웃, 본인 댓글 삭제, 제재 조회, 이의제기는 허용한다.
- 향후 사용자 쓰기 RPC는 동일 `engagement_write` 또는 별도 capability 검사를 의무화한다.

### 11. 서버 액션 오류 구분

**문제**

제재 오류를 일반 권한 오류로 처리하면 UI가 로그인 또는 권한 문제로 잘못 안내할 수 있다.

**보완**

- 제재 강제 함수는 SQLSTATE `P0003`을 사용한다.
- 댓글, 신고, 좋아요, 북마크 서버 액션은 이를 `SANCTIONED`로 매핑한다.
- DB 오류 메시지는 제재 종류와 종료 시각을 포함하되 관리자 메모는 포함하지 않는다.

### 12. 직접 테이블 접근과 immutable 보장

**문제**

RLS만 활성화하고 정책을 만들지 않는 방식은 클라이언트 접근을 막지만 service role 또는 잘못된 후속 migration의 UPDATE/DELETE까지 막지는 못한다.

**보완**

- 원장 테이블에 UPDATE/DELETE 방지 trigger를 둔다.
- projection만 내부 함수가 갱신한다.
- 모든 테이블 권한을 PUBLIC, anon, authenticated에서 회수한다.
- private helper 함수 execute 권한도 회수한다.

## 최종 구현 조건

1. 관리자 계정은 제재 대상 제외
2. warning 중복 허용, 기능 제한 동일 종류 중복 금지
3. 시간 범위를 포함한 effective-state 강제
4. 만료 후 30일 이의제기 허용
5. `revoked`, `expired`, `overturned` 의미 분리
6. 신고 경고 알림 중복 방지
7. 제재 관련 알림 원자 생성
8. 감사 대상·근거 FK 보존
9. account suspension의 댓글·신고·좋아요·북마크 차단
10. SQLSTATE `P0003` 계약
11. immutable trigger와 직접 권한 차단
12. Hosted DB 함수·트리거·권한 및 실제 제한 시나리오 검증
