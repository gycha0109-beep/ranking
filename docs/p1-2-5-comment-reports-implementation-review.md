# P1-2.5 댓글 신고·운영 제재 구현 리뷰

## 검토 범위

- 사용자 댓글 신고 RPC 및 UI
- 신고 상태 조회
- 관리자 신고 사건 대기열
- 사건 단위 처리 및 Moderation 연동
- 감사 이력과 작성자 경고 기록
- 권한, 중복 방지, Rate Limit, 동시성

## 확인 결과

### 데이터 무결성

- `comment_reports`는 댓글과 신고자를 연결하며 신고 사유와 선택적 상세 사유를 저장한다.
- 동일 사용자의 동일 댓글 신고는 부분 UNIQUE 인덱스로 1회만 허용한다.
- 처리 완료 신고는 `comment_report_decisions`의 단일 결정에 연결된다.
- pending/처리완료 상태와 처리 시각·결정 ID 조합을 CHECK 제약으로 강제한다.

### 보안

- anon/authenticated의 두 테이블 직접 권한을 모두 제거했다.
- 사용자 신고 및 상태 조회는 SECURITY DEFINER RPC만 사용한다.
- 관리자 RPC는 내부에서 `auth.uid()`와 `is_admin()`을 재검증한다.
- 신고자 식별자는 관리자 대기열에도 반환하지 않는다.

### 남용 방지

- 자기 댓글 신고를 거부한다.
- 삭제·비공개 댓글 및 공개 경로에서 접근할 수 없는 댓글 신고를 거부한다.
- 사용자별 신고 생성 Rate Limit을 DB에서 강제한다.
- 상세 사유는 정규화하고 길이를 제한한다.

### 운영 처리

- 신고는 댓글별 사건으로 집계된다.
- 처리 시 expected pending count를 검증해 stale 관리자 화면의 오판을 방지한다.
- 댓글별 advisory transaction lock과 행 잠금을 함께 사용한다.
- 기각·유지·숨김·차단 및 작성자 경고를 지원한다.
- 숨김·차단은 기존 append-only Moderation review 흐름을 재사용한다.
- 처리 결정은 별도 append-only 감사 테이블에 기록한다.

## 리뷰 중 보완

- 신고자 개인정보를 큐 응답에서 제외했다.
- 관리자 처리에 pending count optimistic concurrency를 추가했다.
- 삭제된 댓글에 숨김·차단 적용을 금지했다.
- 숨김·차단·경고에는 10자 이상의 관리자 메모를 요구했다.
- 직접 테이블 접근을 제거하고 RPC 경계로 통일했다.

## 결론

구현 범위는 P1-2.5 설계 목표를 충족한다. 병합 전 CI와 호스팅 DB 권한·RPC 계약 검증이 필요하다.
