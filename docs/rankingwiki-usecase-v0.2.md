# 랭킹위키 Usecase 문서 v0.2

## 0. 문서 목적

이 문서는 **랭킹위키의 사용자 행동, 운영 흐름, 기능 범위**를 명료화하기 위한 Usecase 문서다.

이 문서에서는 다음을 다룬다.

- 누가 서비스를 사용하는가
- 사용자는 어떤 목적을 가지고 들어오는가
- 관리자는 어떤 흐름으로 랭킹 문서를 발행하는가
- 콜드 스타트 상황에서 랭킹을 어떻게 다루는가
- MVP에서 반드시 필요한 사용자 흐름은 무엇인가

이 문서에서는 다음을 자세히 다루지 않는다.

- DB ERD
- 테이블 구조
- API 구조
- 화면별 컴포넌트 설계
- 구현 일정
- 코드 구조
- 크롤링 파이프라인

위 항목은 별도 문서에서 다룬다.

---

## 1. 서비스 정의

**랭킹위키**는 다양한 주제의 순위를 모아두고, 각 랭킹의 기준과 이유를 설명하며, 유저가 해당 랭킹에 반응하거나 토론할 수 있는 **랭킹 기반 위키형 아카이브 서비스**다.

서비스는 단순 순위표 사이트가 아니다.

랭킹위키는 다음 세 가지를 결합한다.

1. **랭킹 아카이브**  
   여러 주제의 랭킹 문서를 축적한다.

2. **항목 위키**  
   랭킹에 포함되는 개별 항목의 정보를 누적한다.

3. **반응/토론 레이어**  
   유저가 랭킹에 대해 인정, 비인정, 의견, 댓글을 남길 수 있다.

단, 서비스의 중심은 커뮤니티가 아니라 **랭킹 문서**다.  
반응과 토론은 랭킹 문서의 재미와 신뢰도를 보조하는 참여 기능으로 둔다.

---

## 2. 서비스 핵심 원칙

### 2.1 랭킹 문서가 중심이다

서비스의 핵심 콘텐츠는 댓글이나 게시글이 아니라 **랭킹 문서**다.

랭킹 문서는 다음 정보를 포함해야 한다.

- 무엇에 대한 순위인지
- 어떤 후보군에서 뽑은 순위인지
- 어떤 기준으로 순위를 매겼는지
- 각 항목이 왜 해당 순위인지
- 운영자 선정인지, 유저 참여 기반인지
- 향후 순위가 바뀔 수 있는지

---

### 2.2 위키형 구조는 보조 자산이다

랭킹에 포함된 개별 항목은 별도 상세 페이지를 가질 수 있다.

예시:

- 특정 닭가슴살 제품
- 특정 브랜드
- 특정 웹툰
- 특정 영화
- 특정 게임
- 특정 캐릭터

아이템 상세 페이지는 해당 항목이 어떤 랭킹에 포함되었는지 보여준다.

즉, 구조는 다음과 같다.

```txt
랭킹 문서 = 검색 유입과 핵심 콘텐츠
아이템 페이지 = 내부 연결과 위키형 정보 축적
반응/댓글 = 참여와 검증 레이어
```

---

### 2.3 토론은 처음부터 크게 열지 않는다

랭킹은 논쟁을 유발하기 쉬운 콘텐츠다.

예시:

- 왜 이 제품이 1위인가
- 왜 이 작품이 TOP 10에 없는가
- 인기 기준이면 이 순위가 맞는가
- 실사용 기준이면 다른 결과가 나와야 하지 않는가

따라서 유저 반응과 토론 기능은 필요하다.

다만 MVP 단계에서는 커뮤니티 기능을 크게 열지 않는다.

초기에는 다음 정도로 제한한다.

- 간단한 반응 버튼
- 1단 댓글
- 관리자 숨김 처리

대댓글, 신고, 제재, 유저 간 논쟁 구조는 후순위로 둔다.

---

## 3. 핵심 정보 구조 개념

이 문서는 ERD가 아니므로 기술 구조를 깊게 다루지 않는다.  
다만 Usecase 이해에 필요한 정보 구조 개념은 정의한다.

---

### 3.1 Category

서비스의 큰 주제 분류다.

예시:

- 식품
- 콘텐츠
- 게임
- 영화
- 교육
- 인물

Category는 사이트의 최상위 탐색 구조를 담당한다.

---

### 3.2 Subcategory

Category 아래의 구체 영역이다.

예시:

```txt
식품 > 닭가슴살
식품 > 단백질 보충제
콘텐츠 > 웹툰
콘텐츠 > 영화
게임 > 모바일 게임
```

Subcategory는 실제 랭킹 문서가 많이 생성되는 단위다.

---

### 3.3 Facet

Facet은 랭킹이나 아이템을 세부적으로 분류하는 조건이다.

Category와 Subcategory가 폴더라면, Facet은 필터다.

예시:

### 웹툰

- 플랫폼: 네이버, 카카오, 리디
- 장르: 로맨스, 공포, 액션, 판타지
- 상태: 완결, 연재중
- 목적: 입문 추천, 작화 좋은, 스토리 좋은

### 닭가슴살

- 브랜드: 한끼통살, 허닭, 랭커
- 형태: 수비드, 훈제, 볼, 스테이크
- 목적: 가성비, 다이어트용, 맛있는
- 판매처: 쿠팡, 랭킹닭컴, 편의점

---

### 3.4 Ranking

Ranking은 실제 랭킹 문서다.

예시:

- 2026 닭가슴살 브랜드 순위
- 맛있는 수비드 닭가슴살 TOP 10
- 네이버 로맨스 웹툰 순위
- 입문자용 완결 웹툰 추천 순위
- 가성비 단백질 보충제 순위

Ranking은 하나의 Category/Subcategory에 속하고, 여러 Facet 조건을 가질 수 있다.

---

### 3.5 Ranking Scope

Ranking Scope는 해당 랭킹이 **어떤 후보군에서 순위를 뽑는지** 정의하는 개념이다.

예시:

```txt
랭킹명: 네이버 완결 로맨스 웹툰 TOP 10

Scope:
- Category: 콘텐츠
- Subcategory: 웹툰
- Platform: 네이버
- Genre: 로맨스
- Status: 완결
```

또 다른 예시:

```txt
랭킹명: 맛있는 수비드 닭가슴살 TOP 10

Scope:
- Category: 식품
- Subcategory: 닭가슴살
- Form: 수비드
- Purpose: 맛
```

Ranking Scope가 있어야 사용자가 “이 순위가 어떤 범위 안에서 나온 것인지” 이해할 수 있다.

---

### 3.6 Item

Item은 랭킹에 포함되는 개별 항목이다.

예시:

- 한끼통살 수비드 닭가슴살
- 허닭 닭가슴살
- 랭커 닭가슴살 볼
- 특정 웹툰
- 특정 영화
- 특정 게임

Item은 여러 랭킹에 동시에 포함될 수 있다.

---

### 3.7 Ranking Entry

Ranking Entry는 특정 랭킹 안에서 특정 아이템이 몇 위인지와 왜 그 순위인지를 나타내는 개념이다.

예시:

```txt
Ranking: 맛있는 수비드 닭가슴살 TOP 10
Item: 한끼통살 수비드 닭가슴살
Position: 1
Reason: 식감과 맛 평가가 안정적이고, 초보자 접근성이 높음
```

Ranking Entry에는 최소한 다음 정보가 필요하다.

- 순위
- 아이템
- 선정 이유
- 필요 시 운영자 점수
- 필요 시 참고 메모
- 스폰서 여부 표시 가능성

---

## 4. Actor 정의

### 4.1 방문자

로그인하지 않은 일반 사용자다.

방문자는 주로 읽기 중심으로 행동한다.

가능한 행동:

- 홈 보기
- 카테고리 탐색
- 랭킹 목록 보기
- 랭킹 상세 보기
- 아이템 상세 보기
- 검색
- 댓글과 반응 수 읽기

방문자는 초기 MVP에서 콘텐츠 소비자 역할을 한다.

---

### 4.2 로그인 유저

계정을 만든 사용자다.

가능한 행동:

- 랭킹에 반응 남기기
- 댓글 작성
- 나중에 랭킹 투표 참여
- 나중에 랭킹 제보 또는 수정 제안

MVP에서는 로그인 유저의 역할을 과하게 확장하지 않는다.  
초기에는 반응과 댓글 정도로 제한한다.

---

### 4.3 관리자

랭킹 문서를 만들고 관리하는 운영자다.

가능한 행동:

- 카테고리 생성/수정
- 서브카테고리 생성/수정
- Facet 생성/수정
- 아이템 생성/수정
- 랭킹 생성/수정
- 랭킹에 아이템 연결
- 순위와 선정 이유 작성
- 선정 기준과 Scope 작성
- 발행 상태 관리
- 댓글과 반응 관리

MVP에서 가장 중요한 Actor는 관리자다.  
서비스 초기 성공은 관리자가 랭킹 문서를 얼마나 빠르고 안정적으로 발행할 수 있는지에 달려 있다.

---

### 4.4 시스템

초기에는 자동화 기능을 만들지 않는다.

다만 향후 시스템은 다음 역할을 수행할 수 있다.

- 인기 랭킹 집계
- 조회수 집계
- 반응 데이터 집계
- 외부 데이터 import
- 랭킹 변경 이력 저장
- 유저 투표 데이터 반영
- 크롤링 또는 반자동 수집 파이프라인 연결
- 스폰서 슬롯 관리

MVP에서는 시스템 자동화보다 수동 운영 흐름을 우선한다.

---

## 5. MVP 범위

### 5.1 MVP의 핵심 목표

MVP의 목표는 많은 카테고리를 여는 것이 아니다.

MVP의 핵심 목표는 다음 하나다.

```txt
관리자가 수동으로 랭킹 문서를 만들고,
그 문서가 공개 페이지에 정상 노출되며,
방문자가 순위·기준·선정 이유·아이템 정보를 읽을 수 있다.
```

---

### 5.2 MVP에 반드시 포함할 Usecase

- 방문자가 홈에서 랭킹을 탐색한다.
- 방문자가 카테고리/서브카테고리별 랭킹을 본다.
- 방문자가 랭킹 상세를 본다.
- 방문자가 아이템 상세를 본다.
- 관리자가 랭킹 문서를 만든다.
- 관리자가 랭킹 엔트리를 편집한다.
- 관리자가 랭킹을 미리보기/발행한다.
- 관리자가 기본 카테고리, 서브카테고리, Facet, 아이템을 관리한다.
- 검색, 반응, 댓글 관련 Usecase는 MVP 직후 검토할 P1 범위로 둔다.

---

### 5.3 MVP 직후 검토할 Usecase

- 방문자가 검색한다.
- 로그인 유저가 반응을 남긴다.
- 로그인 유저가 댓글을 작성한다.

---

## 6. 공개 사용자 Usecase

### UC-P01. 방문자가 홈에서 랭킹을 탐색한다

### 목적

방문자가 사이트에 들어와 현재 볼 만한 랭킹을 빠르게 찾는다.

### 기본 흐름

1. 방문자가 홈에 접속한다.
2. 시스템은 대표 랭킹, 최신 랭킹, 주요 카테고리를 보여준다.
3. 방문자는 관심 있는 랭킹을 클릭한다.
4. 랭킹 상세 페이지로 이동한다.

### 성공 기준

- 홈에서 최소 3개 이상의 랭킹이 보인다.
- 주요 카테고리가 보인다.
- 랭킹 클릭 시 상세 페이지로 이동한다.
- 데이터가 없는 경우 빈 상태 안내가 나온다.

---

### UC-P02. 방문자가 카테고리별 랭킹을 본다

### 목적

방문자가 관심 있는 큰 주제의 랭킹을 모아서 본다.

### 기본 흐름

1. 방문자가 카테고리 메뉴를 선택한다.
2. 시스템은 카테고리 목록을 보여준다.
3. 방문자가 특정 카테고리를 선택한다.
4. 해당 카테고리에 속한 서브카테고리와 랭킹 목록이 나온다.

### 성공 기준

- 카테고리별 랭킹 목록이 보인다.
- 빈 카테고리의 경우 적절한 빈 상태 안내가 나온다.
- 서브카테고리가 있는 경우 하위 탐색이 가능하다.

---

### UC-P03. 방문자가 서브카테고리별 랭킹을 본다

### 목적

방문자가 더 구체적인 영역의 랭킹을 본다.

예시:

```txt
식품 > 닭가슴살
콘텐츠 > 웹툰
콘텐츠 > 영화
```

### 기본 흐름

1. 방문자가 특정 서브카테고리에 접속한다.
2. 시스템은 해당 서브카테고리의 랭킹 목록을 보여준다.
3. 사용 가능한 Facet 조건이 있으면 함께 보여준다.
4. 방문자는 원하는 랭킹을 선택한다.

### 성공 기준

- 서브카테고리별 랭킹 목록이 보인다.
- Facet은 보조 정보로 제공된다.
- 랭킹 클릭 시 상세 페이지로 이동한다.

---

### UC-P04. 방문자가 Facet 조건으로 랭킹을 좁혀 본다

### 목적

방문자가 단순 카테고리보다 더 구체적인 조건으로 랭킹을 찾는다.

예시:

```txt
웹툰 + 네이버 + 로맨스 + 완결
닭가슴살 + 수비드 + 가성비
보충제 + 초보자용 + 초코맛
```

### 기본 흐름

1. 방문자가 카테고리 또는 서브카테고리에 들어간다.
2. 시스템은 선택 가능한 Facet 조건을 보여준다.
3. 방문자가 조건을 선택한다.
4. 시스템은 조건에 맞는 랭킹 목록을 보여준다.
5. 방문자는 랭킹 상세로 이동한다.

### 성공 기준

- Facet 조건을 통해 랭킹 목록을 좁혀볼 수 있다.
- 여러 조건을 조합할 수 있는 구조를 가진다.
- MVP에서는 UI를 단순하게 시작한다.

### MVP 범위 참고

MVP에서는 Facet 조건을 랭킹 상세와 목록 카드에 표시하는 것까지를 우선한다.
Facet 다중 필터 UI와 복잡한 조건 조합 탐색은 P1 범위로 둔다.
---

### UC-P05. 방문자가 랭킹 상세를 본다

### 목적

방문자가 단순 순위뿐 아니라 왜 이 순위인지 이해한다.

### 랭킹 상세에 필요한 정보

- 랭킹 제목
- 랭킹 요약
- Ranking Scope
- 랭킹 유형
- 선정 기준
- 기준별 가중치 또는 설명
- 운영자 설명
- 참고 근거
- 최종 업데이트일
- 순위표
- 각 항목별 선정 이유
- 관련 랭킹
- 유저 반응 또는 댓글

### 기본 흐름

1. 방문자가 랭킹 상세에 접속한다.
2. 시스템은 랭킹 제목과 요약을 보여준다.
3. 시스템은 이 랭킹이 어떤 Scope에서 나온 순위인지 보여준다.
4. 시스템은 선정 기준과 랭킹 유형을 보여준다.
5. 시스템은 1위부터 순서대로 아이템을 보여준다.
6. 각 아이템에는 선정 이유가 함께 표시된다.
7. 방문자는 아이템을 클릭해 아이템 상세로 이동할 수 있다.
8. 방문자는 반응 수 또는 댓글을 확인한다.

### 성공 기준

- 랭킹의 범위가 명확히 보인다.
- 랭킹의 기준이 보인다.
- 순위 항목이 position 순서대로 보인다.
- 각 항목마다 선정 이유가 보인다.
- 아이템 상세로 이동 가능하다.
- 운영자 선정 랭킹인지, 유저 참여 랭킹인지 구분된다.

---

### UC-P06. 방문자가 아이템 상세를 본다

### 목적

방문자가 특정 아이템이 어떤 랭킹들에 포함되어 있는지 확인한다.

### 기본 흐름

1. 방문자가 랭킹 상세에서 아이템을 클릭한다.
2. 시스템은 아이템 상세 페이지를 보여준다.
3. 아이템 설명, 이미지, 외부 링크, 관련 Facet을 보여준다.
4. 시스템은 이 아이템이 포함된 랭킹 목록을 보여준다.
5. 방문자는 다른 관련 랭킹으로 이동할 수 있다.

### 성공 기준

- 아이템 기본 정보가 보인다.
- 해당 아이템이 포함된 랭킹 목록이 보인다.
- 관련 랭킹으로 이동할 수 있다.
- 외부 링크나 제휴 링크를 넣을 수 있는 구조를 가진다.

---

### UC-P07. 방문자가 검색한다

### 목적

방문자가 원하는 랭킹이나 아이템을 빠르게 찾는다.

### 검색 대상

- 랭킹 제목
- 랭킹 요약
- 아이템 제목
- 아이템 설명
- 브랜드명
- 제작자명
- Facet

### 기본 흐름

1. 방문자가 검색어를 입력한다.
2. 시스템은 랭킹 결과와 아이템 결과를 나누어 보여준다.
3. 방문자가 원하는 결과를 클릭한다.
4. 해당 상세 페이지로 이동한다.

### 성공 기준

- 검색어와 관련된 랭킹 또는 아이템이 나온다.
- 결과가 없으면 빈 상태 안내가 나온다.
- 랭킹 결과와 아이템 결과가 구분된다.

### MVP 여부

P1 기능이다.  
P0-Core에서는 검색 없이도 홈, 카테고리, 서브카테고리, 랭킹 상세 탐색이 가능해야 한다.

---

## 7. 로그인 유저 Usecase

### UC-U01. 로그인 유저가 랭킹에 반응을 남긴다

### 목적

댓글보다 가볍게 유저 의견 데이터를 쌓는다.

### 가능한 반응 예시

- 인정
- 비인정
- 써봤어요
- 보고 있어요
- 순위 바꿔야 함
- 궁금해요

### 기본 흐름

1. 로그인 유저가 랭킹 상세에 접속한다.
2. 반응 버튼 중 하나를 누른다.
3. 시스템은 반응을 저장한다.
4. 랭킹 상세에 누적 반응 수를 표시한다.

### 성공 기준

- 로그인 유저만 반응할 수 있다.
- 동일 유저의 중복 반응 정책이 존재한다.
- 반응 데이터는 향후 유저 랭킹 또는 신뢰도 보정에 활용 가능해야 한다.

### MVP 여부

P1 기능이다.  
P0-Core에서는 반응 기능 없이도 랭킹 상세를 읽고 탐색할 수 있어야 한다.

---

### UC-U02. 로그인 유저가 댓글을 작성한다

### 목적

랭킹에 대한 유저 의견과 토론을 쌓는다.

### 기본 흐름

1. 로그인 유저가 랭킹 상세 또는 아이템 상세에 접속한다.
2. 댓글을 작성한다.
3. 시스템은 댓글을 저장한다.
4. 댓글 목록에 표시한다.

### 초기 제한

- 대댓글은 제외한다.
- 추천/비추천은 제외한다.
- 신고 기능은 제외한다.
- 1단 댓글만 허용한다.

### 성공 기준

- 로그인한 유저만 댓글 작성 가능하다.
- 비로그인 유저는 댓글 읽기만 가능하다.
- 댓글에는 작성자, 내용, 작성일이 보인다.
- 관리자가 댓글을 숨길 수 있다.

### MVP 여부

P1 기능이다.  
랭킹 문서 발행 루프가 먼저 완성된 뒤 도입한다.

## 8. 관리자 Usecase

### UC-A01. 관리자가 카테고리를 만든다

### 목적

랭킹을 분류할 큰 주제를 만든다.

### 입력 정보

- 카테고리명
- 설명
- 노출 여부

### 기본 흐름

1. 관리자가 CMS에 접속한다.
2. 카테고리 생성 화면으로 이동한다.
3. 카테고리 정보를 입력한다.
4. 저장한다.
5. 공개 페이지에서 해당 카테고리가 보인다.

### 성공 기준

- 카테고리가 생성된다.
- 공개 카테고리 목록에 노출된다.
- 중복 이름 또는 중복 주소를 방지한다.

---

### UC-A02. 관리자가 서브카테고리를 만든다

### 목적

카테고리 아래에 실제 랭킹이 모일 구체 영역을 만든다.

### 입력 정보

- 상위 카테고리
- 서브카테고리명
- 설명
- 노출 여부

### 기본 흐름

1. 관리자가 상위 카테고리를 선택한다.
2. 서브카테고리 정보를 입력한다.
3. 저장한다.
4. 랭킹 생성 시 해당 서브카테고리를 선택할 수 있다.

### 성공 기준

- 서브카테고리가 상위 카테고리 아래에 연결된다.
- 랭킹 생성 시 선택 가능하다.

---

### UC-A03. 관리자가 Facet을 만든다

### 목적

랭킹과 아이템을 세부 조건으로 분류하기 위한 필터값을 만든다.

### 입력 정보

- Facet 그룹
- Facet 이름
- 설명
- 사용 영역

### Facet 그룹 예시

| Facet 그룹 | 예시 |
|---|---|
| platform | 네이버, 카카오, 리디 |
| genre | 로맨스, 공포, 액션 |
| brand | 한끼통살, 허닭, 랭커 |
| form | 수비드, 훈제, 볼, 스테이크 |
| purpose | 가성비, 다이어트, 입문 추천 |
| status | 완결, 연재중, 판매중 |

### 기본 흐름

1. 관리자가 Facet 관리 화면으로 이동한다.
2. Facet 그룹을 선택하거나 생성한다.
3. Facet 값을 입력한다.
4. 저장한다.
5. 랭킹 또는 아이템 생성 시 해당 Facet을 연결할 수 있다.

### 성공 기준

- Facet은 카테고리 트리를 대체하지 않고 필터 역할을 한다.
- 랭킹과 아이템에 연결할 수 있다.
- Facet 그룹이 있어 조건의 성격을 구분할 수 있다.

---

### UC-A04. 관리자가 아이템을 만든다

### 목적

랭킹에 들어갈 개별 항목을 미리 등록한다.

### 입력 정보

- 아이템명
- 설명
- 이미지
- 아이템 유형
- 브랜드 또는 제작자
- 외부 링크
- 제휴 링크
- 관련 Facet

### 아이템 유형 예시

| 아이템 유형 | 예시 |
|---|---|
| food | 닭가슴살 제품 |
| supplement | 단백질 보충제 |
| webtoon | 웹툰 |
| movie | 영화 |
| game | 게임 |
| person | 인물 |
| brand | 브랜드 |

### 기본 흐름

1. 관리자가 아이템 생성 화면으로 이동한다.
2. 아이템 기본 정보를 입력한다.
3. 관련 Facet을 연결한다.
4. 저장한다.
5. 랭킹 생성 시 해당 아이템을 선택할 수 있다.

### 성공 기준

- 아이템이 생성된다.
- 아이템 상세 페이지가 생성된다.
- 랭킹 생성 시 검색/선택 가능하다.

---

### UC-A05. 관리자가 랭킹 문서를 만든다

### 목적

하나의 완성된 랭킹 콘텐츠를 작성한다.

### 입력 정보

- 랭킹 제목
- 카테고리
- 서브카테고리
- Ranking Scope
- 관련 Facet
- 랭킹 유형
- 요약
- 선정 기준
- 기준별 가중치 또는 설명
- 참고 근거
- 본문 설명
- 발행 상태
- SEO 제목
- SEO 설명

### 기본 흐름

1. 관리자가 랭킹 생성 화면으로 이동한다.
2. 랭킹 제목과 요약을 입력한다.
3. 카테고리와 서브카테고리를 선택한다.
4. 이 랭킹의 Scope를 정의한다.
5. 관련 Facet을 연결한다.
6. 랭킹 유형을 선택한다.
7. 선정 기준과 기준 설명을 입력한다.
8. 참고 근거와 본문 설명을 입력한다.
9. draft로 저장한다.

### 성공 기준

- 랭킹 문서가 생성된다.
- draft 상태에서는 관리자만 볼 수 있다.
- published 상태 전까지 공개 페이지에는 노출되지 않는다.
- Ranking Scope와 선정 기준이 비어 있으면 발행을 막거나 경고한다.

---

### UC-A06. 관리자가 랭킹 엔트리를 편집한다

### 목적

랭킹 문서 안에 들어갈 순위표를 만든다.

### 관리자가 할 수 있어야 하는 일

- 아이템 검색
- 아이템 추가
- 아이템이 없으면 즉석 생성
- 아이템 제거
- 순위 변경
- 선정 이유 작성
- 운영자 점수 입력
- 참고 메모 작성
- 스폰서 여부 표시 가능성 유지

### 기본 흐름

1. 관리자가 랭킹 편집 화면에서 아이템을 검색한다.
2. 랭킹에 포함할 아이템을 추가한다.
3. 각 아이템에 순위를 입력한다.
4. 각 아이템에 선정 이유를 작성한다.
5. 필요 시 점수 또는 참고 메모를 입력한다.
6. 저장한다.
7. 미리보기에서 순위표를 확인한다.

### 성공 기준

- 순위가 정확한 순서로 표시된다.
- 각 순위마다 선정 이유가 보인다.
- 아이템 추가/삭제/순위 변경이 가능하다.
- 공개 페이지에 변경 사항이 반영된다.

---

### UC-A07. 관리자가 랭킹을 미리보기한다

### 목적

발행 전 공개 페이지에서 어떻게 보일지 확인한다.

### 기본 흐름

1. 관리자가 랭킹 편집 화면에서 미리보기를 클릭한다.
2. 시스템은 공개 페이지와 유사한 형태로 미리보기를 보여준다.
3. 관리자는 누락된 정보나 문구를 확인한다.
4. 필요 시 다시 편집한다.

### 성공 기준

- 공개 전에도 랭킹 상세 형태를 확인할 수 있다.
- 누락된 필수 정보가 있으면 경고한다.
- 미리보기는 일반 방문자에게 노출되지 않는다.

---

### UC-A08. 관리자가 랭킹을 발행한다

### 목적

작성한 랭킹 문서를 공개 상태로 전환한다.

### 기본 흐름

1. 관리자가 랭킹 문서를 작성한다.
2. 랭킹 엔트리를 추가한다.
3. 선정 기준과 Scope를 확인한다.
4. 미리보기로 최종 확인한다.
5. published 상태로 변경한다.
6. 공개 페이지에 노출된다.

### 성공 기준

- published 상태의 랭킹만 공개 페이지에 노출된다.
- 필수 정보가 누락된 경우 발행을 막거나 경고한다.
- 발행 후 공개 URL로 접근 가능하다.

---

### UC-A09. 관리자가 댓글과 반응을 관리한다

### 목적

유저 참여 기능이 사이트 품질을 해치지 않게 관리한다.

### 기본 흐름

1. 관리자가 댓글/반응 관리 화면으로 이동한다.
2. 특정 랭킹의 댓글과 반응을 확인한다.
3. 부적절한 댓글을 숨김 처리한다.
4. 필요 시 삭제 처리한다.

### 성공 기준

- 부적절한 댓글을 공개 페이지에서 숨길 수 있다.
- 관리자는 랭킹별 반응 현황을 확인할 수 있다.

### MVP 여부

댓글과 반응 기능이 도입된 뒤 필요하다.  
초기 P0-Core에는 포함하지 않아도 된다.

## 9. 랭킹 기준 및 콜드 스타트 Usecase

### UC-R01. 관리자가 운영자 큐레이션 랭킹을 만든다

### 목적

유저 데이터가 없는 초기 단계에서도 랭킹 문서를 발행할 수 있게 한다.

### 기본 정책

초기 랭킹은 유저 투표가 아니라 운영자 큐레이션으로 시작한다.

단, 다음 정보를 명확히 공개한다.

- 운영자 선정 랭킹임
- 어떤 후보군에서 선정했는지
- 어떤 기준을 사용했는지
- 기준별 가중치 또는 설명
- 향후 유저 반응에 따라 조정될 수 있음

### 기본 흐름

1. 관리자가 후보군을 수집한다.
2. 후보군의 공통 조건을 정리한다.
3. Ranking Scope를 정의한다.
4. 카테고리에 맞는 기준표를 작성한다.
5. TOP 5 또는 TOP 10을 선정한다.
6. 각 항목의 선정 이유를 작성한다.
7. 운영자 큐레이션 랭킹임을 표시한다.
8. 발행한다.

### 성공 기준

- 사용자가 순위의 기준을 이해할 수 있다.
- 운영자 감으로 만든 순위처럼 보이지 않는다.
- 향후 유저 참여 랭킹과 구분 가능하다.

---

### UC-R02. 관리자가 후보군을 정리해 랭킹 엔트리를 구성한다

### 목적

임의 순위가 아니라 후보군 기반의 랭킹을 만든다.

### 기본 흐름

1. 관리자가 후보군을 30~50개 정도 수집한다.
2. 중복, 부적합 항목을 제거한다.
3. Ranking Scope와 맞는 항목만 남긴다.
4. 카테고리별 기준표를 적용한다.
5. 상위 항목을 선정한다.
6. 각 항목에 선정 이유를 작성한다.

### 성공 기준

- 랭킹 후보군의 범위가 설명된다.
- 최종 TOP 5 / TOP 10이 기준에 따라 정리된다.
- 선정 제외 항목이 있다면 내부 메모로 남길 수 있다.

---

### UC-R03. 방문자가 랭킹 유형을 구분한다

### 목적

방문자가 현재 보고 있는 랭킹이 어떤 성격인지 이해한다.

### 랭킹 유형 예시

| 랭킹 유형 | 설명 | 예시 |
|---|---|---|
| editor_pick | 운영자가 기준표로 선정 | 2026 닭가슴살 TOP 10 |
| popularity | 조회수/리뷰량/검색량 기반 | 인기 웹툰 순위 |
| quality | 품질/완성도 중심 | 작품성 좋은 영화 순위 |
| purpose | 특정 목적 기반 | 다이어트용 닭가슴살 순위 |
| user_vote | 유저 참여 기반 | 유저가 뽑은 웹툰 순위 |
| sponsored | 광고/제휴 기반 | 스폰서 추천 제품 |

### 기본 흐름

1. 방문자가 랭킹 상세에 접속한다.
2. 시스템은 랭킹 유형을 표시한다.
3. 방문자는 이 랭킹이 운영자 선정인지, 유저 참여 기반인지, 스폰서인지 이해한다.

### 성공 기준

- 랭킹 유형이 명확히 표시된다.
- 운영자 랭킹과 유저 투표 랭킹이 섞이지 않는다.
- 스폰서 항목은 명확히 구분된다.

---

## 10. 향후 수익화 시 고려할 Usecase

### UC-S01. 방문자가 스폰서 항목을 일반 순위와 구분한다

### 목적

수익화가 사이트 신뢰도를 해치지 않게 한다.

### 기본 정책

스폰서 항목은 일반 에디터 순위와 명확히 구분한다.

권장 방식:

```txt
TOP 10 랭킹
+
스폰서 추천 영역
```

일반 순위 안에 스폰서 항목을 섞을 경우 반드시 표시한다.

### 성공 기준

- 스폰서 항목은 표시된다.
- 스폰서가 순위 점수에 영향을 주는지 명확히 안내한다.
- 사용자가 광고성 노출을 일반 순위로 오해하지 않는다.

### MVP 여부

P2 기능이다.  
MVP에서는 정책만 정의하고 실제 스폰서 판매 기능은 만들지 않는다.

## 12. 초기 운영 시나리오

초기 운영자는 다음 흐름으로 콘텐츠를 만든다.

```txt
1. 관리자 로그인

2. Category 생성
   예: 식품

3. Subcategory 생성
   예: 닭가슴살

4. Facet 생성
   예:
   - 브랜드: 한끼통살, 허닭, 랭커
   - 형태: 수비드, 훈제, 볼
   - 목적: 가성비, 다이어트용, 맛있는

5. Item 생성
   예:
   - 한끼통살 수비드 닭가슴살
   - 허닭 수비드 닭가슴살
   - 랭커 닭가슴살 볼

6. Ranking 생성
   예: 2026 맛있는 수비드 닭가슴살 TOP 10

7. Ranking Scope 정의
   예:
   - Category: 식품
   - Subcategory: 닭가슴살
   - Form: 수비드
   - Purpose: 맛

8. 선정 기준 입력
   예:
   - 맛/식감
   - 가격/가성비
   - 리뷰/인지도
   - 구매 접근성

9. Ranking Entry 추가
   예:
   - 1위: 한끼통살 수비드
   - 2위: 허닭 수비드
   - 3위: 랭커 수비드

10. 각 순위별 선정 이유 작성

11. 미리보기

12. published로 발행

13. 공개 페이지 확인
```

## 13. 최종 Usecase 결론

랭킹위키 MVP는 다음 흐름을 검증하는 것이 핵심이다.

```txt
관리자가 수동으로 신뢰 가능한 랭킹 문서를 빠르게 만들고,
방문자는 그 랭킹의 범위·기준·이유·항목 정보를 읽으며,
사이트 내부에서 관련 랭킹과 아이템을 계속 탐색할 수 있다.
```

이 문서에서 가장 중요한 결론은 다음 네 가지다.

1. 서비스 중심은 커뮤니티가 아니라 랭킹 문서다.
2. 카테고리와 Facet은 역할을 분리한다.
3. 랭킹은 반드시 Scope와 기준을 가진다.
4. MVP의 핵심은 관리자 발행 루프다.
