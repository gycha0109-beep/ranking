# P1-2.8 구현 리뷰

## 결론

역할 문자열만 검사하던 기존 구조를 역할 수준과 capability 판정으로 분리했다. 라우트, 서버 액션, SECURITY DEFINER RPC가 동일 capability 계약을 사용하며 고위험 작업은 최고 관리자에게만 허용한다.

## 구현 리뷰에서 확인한 사항

### 1. 모더레이터 권한 과다 부여

초기 capability 표에서는 모더레이터에게 신고 검토와 제재 조회까지 허용할 여지가 있었다. 최종 구현에서는 모더레이터를 `admin_console_access`, `moderation_review`로 제한했다. 신고 사건, 제재, CMS 변경은 관리자 이상만 접근한다.

### 2. `is_admin()` 의미 보존

기존 CMS와 신고 RPC가 `is_admin()`에 의존한다. 이를 모더레이터까지 확장하면 의도하지 않은 CMS 쓰기 권한이 발생한다. 최종적으로 `is_admin()`은 `admin | super_admin`만 참이며, 모더레이터 전용 경로는 별도 capability 검사로 전환했다.

### 3. 역할 변경 경쟁 상태

초기 구현은 대상 사용자별 advisory lock만 사용했다. 서로 다른 최고 관리자 두 명을 동시에 강등하면 양쪽 요청이 마지막 최고 관리자 수 검사를 통과할 수 있다. 모든 역할 변경이 먼저 전역 `admin-role-global` advisory transaction lock을 획득하도록 reconciliation migration을 추가했다.

### 4. 제재 고위험 경계

- 경고: 관리자 이상
- 일반 기간 제한 및 7일 이하 계정 활동 제한: 관리자 이상
- 7일 초과 계정 활동 제한: 최고 관리자
- 제재 조기 해제: 최고 관리자
- 이의제기 기각: 관리자 이상
- 이의제기 수용: 최고 관리자

서버 화면과 액션의 노출 제어는 편의 기능이며 최종 강제는 RPC 내부에서 수행한다.

### 5. 역할 변경 안전성

- 자기 역할 변경 차단
- 마지막 최고 관리자 제거 차단
- 전역 lock 후 대상별 lock 획득
- 한 사용자에게 계층 역할을 누적 저장하되 `private.get_admin_role_level`이 최고 수준을 결정
- 변경 전 기존 운영 역할을 제거하고 새 수준의 계층 역할을 원자적으로 삽입
- 모든 변경을 Append-only 원장에 기록

### 6. 직접 테이블 쓰기 차단

`authenticated`의 `user_roles` INSERT/UPDATE/DELETE 권한을 회수했다. 역할 변경은 최고 관리자 전용 RPC만 사용한다. private 역할 변경 helper는 브라우저 역할에서 실행할 수 없다.

### 7. 화면 접근과 데이터 접근

미들웨어는 경로별 capability를 검사한다. 서버 액션과 RPC도 다시 검사하므로 미들웨어 우회나 직접 RPC 호출로 권한을 확대할 수 없다.

### 8. 감사 통합

역할 변경, 수동 Moderation, 댓글 신고 결정, 제재 이벤트, 이의제기 결정을 단일 읽기 RPC로 통합했다. 원본 원장을 수정하거나 복제하지 않고 UNION 기반 읽기 모델을 제공한다.

## 잔여 리스크

- 현재 역할 수준은 고정 capability 매핑이다. 조직 규모가 커지면 별도 role-capability 테이블과 승인 워크플로가 필요하다.
- 영구 정지와 관리자 계정 제재는 범위 밖이다.
- 이중 승인 또는 사후 승인 큐는 후속 단계로 남긴다.
